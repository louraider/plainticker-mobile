# SKR integration — plan of record

**Decided 2026-09-13 by the founder: the SKR bonus track is in, and it is not optional.** This
replaces plan section 8's "decide at the Sep 24 checkpoint". The checkpoint keeps its other job.

## Why it is worth more than the separate pool suggests

The published pages say the bonus is a separate $10,000 in SKR and that four criteria are worth 25%
each. The Align platform's own hackathon record says something else: `globalScoringCriteria` of AI
20 / **SKR Integration 20** / UX 15 / UI 15 / Innovation 15 / Ecosystem Impact 15
(`docs/hackathon-rules-2026-09-10.md`, S11). That record is marked `"state":"Draft"` and the Terms
prevail, so this is an observation and not a rule. It is also a fifth of the score if the platform
rubric is what judges actually see, which is reason enough to treat the track as core rather than
as a bonus.

The submission form asks for it in words: a 5,000-character answer to "DOES YOUR APPLICATION HAVE
AN SKR INTEGRATION? IF SO, HOW?". Whatever ships has to be describable in one honest paragraph.

What the organisers say counts: "Use SKR for in-app purchases, staking, rewards, access, or invent
your own use case", judged as "a creative and meaningful SKR integration".

## The measurement the threshold rests on

One `getProgramAccounts` over the whole staking program with the same 8-byte slice, 2026-09-13,
against the public RPC (1.0 s, 47,965 accounts):

| | |
|---|---|
| stake accounts | 47,965 |
| with a non-zero principal | 46,436 |
| total staked, one outlier excluded | 4,389,047,810 SKR |
| median stake | 6,719 SKR |
| **accounts holding exactly 10,000.000000 SKR** | **6,189** |

| percentile | staked SKR |
|---|---|
| p25 | 2,454 |
| p50 | 6,719 |
| p70 and p75 | **10,000** |
| p90 | 31,381 |
| p99 | 249,218 |

| threshold | wallets clearing it |
|---|---|
| 1,000 SKR | 38,039 (81.9%) |
| 5,000 SKR | 28,050 (60.4%) |
| **10,000 SKR** | **16,992 (36.6%)** |
| 31,210 SKR | 4,674 (10.1%) |

**N = 10,000 SKR.** It is not a round number picked for looking round: 6,189 wallets sit exactly on
it, which is why p70 and p75 are the same figure, and it separates the engaged third of stakers
from the rest. A tenth of that unlocks for four wallets in five and means nothing; three times it
unlocks for one in ten and reads as a whale gate.

**One account in the program carries an impossible principal**, 11,452,317,590,968,446,072 raw,
about 1.1 × 10^13 SKR unsigned. **Corrected 2026-09-13 while building the vote:** `SkrStakeAccount`
decodes into a signed `Long` and that value does not fit one, so the shipped decoder actually
produces **-6,994,426,482,741,105,544**. A bound written only as "refuse anything above the staked
supply" would have let it straight through. The bound has to close both ends. It is almost certainly not a stake account at all but another 169-byte
account in the same program whose bytes at 105 are something else. The naive read misinterprets it,
so the app must bound what it will print rather than print whatever decodes. An app whose whole
claim is that it refuses figures it cannot stand behind does not get to make an exception for its
own feature.

## What ships, in three layers

The order is deliberate: each layer stands on its own if the one after it never lands.

### A. The reading — "what your SKR actually is"

A block on Portfolio that reads the connected wallet's staked SKR through the bounded forwarder and
states three things nobody else will:

1. **This is principal, not your balance.** The Seeker wallet shows a larger number because it adds
   accrued rewards. Measured on this device: the wallet said 35,474 SKR where the principal is
   38,406.150222. The app does not read rewards and says which number it is showing.
2. **The slot and the age of the read**, exactly as every other chain read in this app carries them.
3. **The bound.** The forwarder lets exactly eight bytes of this account through. That is a fact
   about the app's own architecture and it belongs on the screen, not only in the README.

This is the creative half, and it is the only one of the three that could not be bolted onto any
other entry: it is this product's thesis, disclosure of what a token actually is, turned on Solana
Mobile's own token.

### B. The entitlement — stake-to-unlock, with its own weakness disclosed

At or above **10,000 SKR** the Pro sections unlock. Free forever and never gated: the list, the
trust layer, the premium against the NYSE close, proof of reserves, issuer controls, the swap.

On the same screen, in the app's own voice: **this gate runs on the phone and can be bypassed.**
The real entitlement is wallet-bound and server-verified, and that migration is written down in
`TODOS.md` rather than pretended. During the hackathon everything is free and the screen says so.

This is the meaningful half. It is the actual monetization mechanism from plan section 7, not a
payment checkbox, and stating that a paywall is bypassable is the same act as withholding a premium
off an $80 pool.

### C. The loop — SKR-weighted coverage curation

**Superseded 2026-09-13 by `docs/skr-curation-spec-2026-09-13.md`, which is the design of record.**
The nonce flow below is not what ships: the vote is a memo transaction, so the signer is the voter
by construction and no signature verification is added to the production web app. It is kept only
as the alternative that was weighed and rejected.

On an xStock the analysis does not cover, "Vote to cover next": the app signs a server nonce with
`signMessages`, the server verifies ed25519, reads the voter's staked principal through the
forwarder, and records the vote with that weight. A "Next up" strip shows the leaders, and the
prewarm run covers the winner.

This is the daily-return mechanic and it closes a real loop: vote, then the analysis appears.
Known weakness to state in the README rather than hide: a balance-weighted vote is gameable by a
whale.

A and B are this repository alone and do not wait on anything. C needs the PlainTicker server
repository, which is private and separate.
